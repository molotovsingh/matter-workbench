## Verdict

Conditional GO for a supervised 5-10 lawyer private beta only after one fresh
`c75c6d1` deployment closeout proves the live URL is running this commit and the
operator can still pass the full RC closure pack.

NO-GO for widening beyond trusted supervised testers. The product has the right
shape for the narrow beta, but the evidence is not yet strong enough for broader
access, public-ish exposure, self-service onboarding, or unsupervised legal use.

The main issue is not that the app looks broken. It is that the current evidence
proves many important release gates, but it does not yet prove the whole lawyer
journey in one live end-to-end drill from fresh matter upload through generated
legal output and in-app problem reporting.

## Top Findings

### P1 - Add a single lawyer-journey acceptance drill before handoff

The code has the right surfaces: login, add/find matter, automatic preparation,
Source Labels, List of Dates, Copilot, configurable skills, Activity, and beta
feedback. The tester brief also asks lawyers to exercise that exact flow
(`docs/private-beta-tester-brief.md:31-47`).

The release evidence, however, explicitly says the RC closure pack does not run
paid AI preparation stages or prove perfect legal output
(`docs/private-beta-rc-closure-pack.md:86-95`). The latest UI hardening pass
proves the shell, matter picker, feedback entry, Copilot tier selector, Skills,
Activity, Settings, secret-leak check, and mobile overflow
(`docs/private-beta-ui-hardening-passes/private-beta-ui-hardening-2026-06-08T05-42-25-230Z/ui-hardening-report.md:9-23`).
That is valuable, but it is not the same as proving a lawyer can create or open a
matter, run preparation, review generated chronology, ask Copilot, run a custom
skill, and file feedback in one coherent session.

Fix: add a `private-beta:lawyer-journey-drill` or equivalent acceptance pack.
Use a disposable matter, named tester account, runtime DB mode, provider keys,
and assertions for:

- login succeeds;
- create matter or open seeded matter succeeds;
- upload/add-files custody is visible;
- automatic preparation reaches either `prepared` or an explicit advisory;
- Source Labels and List of Dates are opened and have source-backed content;
- Copilot answers one question with validated citations or fails closed with a
  lawyer-readable reason;
- one custom skill run writes an output or produces a clear overwrite gate;
- Activity records the run state;
- the feedback button stores a problem report with screen, matter, viewport,
  provider route, and recent activity context.

This is the highest-value missing proof for 5-10 trusted lawyers.

### P1 - Fresh closeout is needed for current HEAD

Checked-in live VM closeout evidence is strong, but it is not for this exact
commit. The latest checked-in RC closure pack passed all gates for commit
`ec4ca4e` (`docs/private-beta-rc-closure-packs/private-beta-rc-closure-pack-2026-06-08T04-54-05-116Z.md:1-24`).
The repo now sits at `c75c6d1`.

Fix: deploy `c75c6d1` or confirm the intended deployed commit, then run:

```bash
npm run private-web:readiness-check
npm run private-beta:auth-preflight -- --base-url http://127.0.0.1:4191
npm run private-beta:tester-handoff-drill -- --base-url http://127.0.0.1:4191 --users-file ~/.config/matter-workbench/private-beta-users.json --feedback-ledger ~/.local/share/matter-workbench/private-beta-feedback-ledger.json
npm run private-beta:rc-closure-pack
```

Do not hand out a URL for this checkpoint until the fresh pack passes, because
the readiness docs make current-commit closure a stop rule
(`docs/private-web-beta-readiness-pack.md:189-200`).

### P2 - Bug evidence can still be thin when command interactions are absent

The in-app feedback path captures useful context from the command panel:
screen, view, route, active matter, runtime mode, viewport, recent activity,
provider route, and visible error (`react-ui/src/components/command/CommandPanel.tsx:278-301`).
The Activity page also exposes feedback review and copy/export controls.

But the checked-in bug evidence pack shows a successful pack with "No recent
command interactions captured" (`docs/private-beta-bug-evidence-packs/private-beta-bug-evidence-pack-2026-06-08T04-25-47-670Z.md:26-42`).
That means a real beta bug can still arrive without the action trail needed to
debug "I clicked X and Y happened."

Fix: make the lawyer-journey drill assert that recent activity/command context is
present after Copilot, preparation, custom skill, and feedback. Where command
logging is fire-and-forget, consider surfacing "no command trace captured" in the
feedback packet as a visible operator warning rather than burying it in the
evidence pack.

### P2 - Security posture is private-beta appropriate, not wider-hosting ready

The auth service is reasonable for a narrow beta: auth is disabled unless
explicitly required, required auth fails closed without credentials, sessions are
random in-memory tokens, tester account files are PBKDF2-hashed, disabled users
lose sessions on refresh, cookies are `HttpOnly` and `SameSite=Strict`, and
`Secure` is inferred from an HTTPS public URL
(`services/private-beta-auth-service.mjs:20-31`,
`services/private-beta-auth-service.mjs:72-130`,
`services/private-beta-auth-service.mjs:181-257`,
`services/private-beta-auth-service.mjs:342-363`).

The readiness pack also blocks missing HTTPS URL, missing auth, insecure cookie
posture, missing runtime DB custody, and missing/non-HTTPS mothership sync
(`docs/private-web-beta-readiness-pack.md:134-143`).

The service still binds to `0.0.0.0` for the private VM service and relies on the
deployment boundary/reverse proxy/private access posture
(`deployment/private-vm/matter-workbench-runtime.service:8-15`). That is fine for
the current private VM shape, but it is not a public SaaS boundary. Before
widening, add stronger host hardening, per-user operational auditing, CSRF/rate
limit review for wider browser exposure, and a clear credential lifecycle.

### P2 - Legal output guardrails are good, but legal sampling is still required

Copilot is source-bounded and fails closed when an answered or partial answer
lacks validated source citations (`services/matter-copilot-service.mjs:74-103`,
`services/matter-copilot-service.mjs:180-215`). The global legal policy tells
model-backed work not to invent facts, to preserve uncertainty and date
precision, to separate source-supported facts from legal characterization, and
to treat drafts as lawyer-review work product
(`shared/legal-workbench-policy-prompt.mjs:1-38`).

That is a strong engineering posture. It does not replace legal-output review.
Before widening, run a lawyer-reviewed golden sample across Copilot, List of
Dates, Source Labels, and at least one custom skill. The acceptance result should
record missed central events, unsupported legal characterizations, confusing
citations, and whether "cautious but useful" is actually true for lawyers.

### P2 - `xlsx` remains an accepted private-beta risk, not a widening-ready dependency

`npm audit --omit=dev --json` still reports one high-severity production
dependency issue for `xlsx@0.18.5`: prototype pollution
(`GHSA-4r6h-8v6p-xvw6`) and ReDoS (`GHSA-5pgg-2g8v-p4x9`). The repo has a
clear private-beta disposition for this risk
(`docs/security/npm-audit-disposition.md:11-31`): accepted only for private,
trusted-operator beta, not for public hosted access.

That disposition is defensible for 5-10 trusted lawyers only if uploads remain
authenticated, private, and supervised. Before any wider access, replace or
isolate spreadsheet parsing, add stricter spreadsheet file-size/runtime controls,
or move this parser behind a safer worker boundary.

## Stage Review

### 1. Product Beta Review

Status: conditional pass for supervised beta.

The app gives lawyers a clear starting point: Home offers "Add a new matter",
"Find an existing matter", and a short explanation of the workflow
(`react-ui/src/views/HomeLanding.tsx:101-178`). An active matter shows metadata,
preparation status, stage artifacts, AI run receipts, rerun advice, and a
Preparation Advisory (`react-ui/src/views/MatterOverview.tsx:35-90`,
`react-ui/src/views/MatterOverview.tsx:130-220`). Automatic preparation is
implemented as a real multi-stage runner for setup, extraction, source labels,
List of Dates, story, and advisory checks
(`react-ui/src/lib/autoPreparationRunner.ts:12-19`,
`react-ui/src/lib/autoPreparationRunner.ts:57-134`,
`react-ui/src/lib/autoPreparationRunner.ts:201-218`).

The command panel supports Copilot/model selection, "new skill", "find a
matter", "prepare matter", command suggestions, recent activity, and the
problem-report form (`react-ui/src/components/command/CommandPanel.tsx:415-687`).

Product concern: the latest browser evidence proves the shell and major pages,
not the whole lawyer journey with live provider-backed outputs.

### 2. Ops Review

Status: pass for supervised private beta, pending fresh `c75c6d1` closeout.

Ops is unusually strong for this stage. The repo has commands for deploy,
rollback, service checks, ops packs, security checks, recoverability, readiness,
tester handoff, auth preflight, bug evidence, RC closure, UI hardening, and
runtime DB browser acceptance (`package.json:11-25`, `package.json:68-72`).

The deployment docs describe a repeatable tracked-file rsync deployment, build
before symlink switch, service restart, VM-local service check, and rendered UI
hardening pass (`docs/private-beta-codex-deployment.md:94-142`). Rollback is
explicit and verified with service/UI checks (`docs/private-beta-codex-deployment.md:163-176`).

Ops concern: current HEAD needs its own closeout evidence before handoff.

### 3. Security Review

Status: conditional pass for private beta only.

Strengths:

- private-beta auth is explicit and fail-closed;
- tester account files are hashed and reloadable;
- disabled tester accounts invalidate sessions;
- cookies are `HttpOnly`, `SameSite=Strict`, and `Secure` under HTTPS config;
- local `private-beta:tester-handoff-drill` passed against a disposable
  auth-required server during this review;
- readiness blocks missing HTTPS/auth/runtime DB/mothership posture;
- security check covers private/loopback access posture, env file permissions,
  service template posture, audit disposition, runtime DB role proof, and live
  service smoke.

Boundary:

- static React assets are intentionally public enough for the login shell to
  load, while APIs are auth-gated;
- the Node service binds to `0.0.0.0` behind the private VM boundary;
- `xlsx` remains an explicitly accepted private-beta dependency risk for
  spreadsheet extraction;
- no self-service signup/password reset is claimed;
- this is not a public web app.

### 4. Data Integrity Review

Status: conditional pass, with live journey proof still needed.

Runtime DB custody is implemented as a materialization adapter: reads materialize
DB payloads into a temporary matter workspace and clean up afterward; writes
materialize the workspace, run the existing workflow, persist changed artifacts,
and tombstone deleted artifacts (`services/runtime-db-storage-service.mjs:455-554`).
Workflow routes use that adapter for matter init, extraction, source labels,
List of Dates, label refresh, story, doctor, context, Copilot, and rerun advice
(`routes/matter-workflow-routes.mjs:31-220`,
`routes/matter-workflow-routes.mjs:242-460`).

Upload custody has runtime DB create/add-files paths, path validation, overlap
checks, and tests for payload bytes, row locking, and append intake behavior. The
targeted test pass covered runtime DB storage, upload APIs, source labels,
List of Dates contracts, matter context, and Copilot citation validation.

Data concern: the current checked-in evidence should be extended with a fresh
runtime DB matter that proves upload -> extraction -> Source Index -> List of
Dates -> advisory -> skill output custody in one acceptance artifact.

### 5. Legal-Output Review

Status: conditional pass for beta; not ready for unsupervised reliance.

The system is designed to be cautious without being inert: Copilot receives a
bounded matter packet and must cite validated sources; custom skills receive
source-backed matter context; List of Dates policy preserves date precision and
lawyer-facing source labels; the visible UI warns that source-backed answers are
one question at a time and do not remember earlier chat
(`react-ui/src/components/command/CommandPanel.tsx:603-604`).

Legal concern: engineering guardrails prove failure modes and source constraints.
They do not prove legal usefulness. Widening access needs lawyer-reviewed output
sampling.

## Go Criteria For 5-10 Trusted Lawyers

Hand out the URL only when all of these are true:

- `private-web:readiness-check` has no blockers.
- Current deployed commit equals the intended release commit.
- Fresh `private-beta:rc-closure-pack` passes for that commit.
- Fresh UI hardening pass has zero console errors and no meaningful mobile
  overflow.
- The new lawyer-journey drill passes or records only known non-blocking
  advisory limitations.
- Runtime DB write smoke and recoverability pack pass.
- Operator can identify and execute rollback.
- Mothership feedback and diagnostic signal sync are configured.
- Testers get named accounts and the tester brief.

## Widening Criteria

Do not widen beyond the supervised 5-10 lawyer circle until these are done:

- lawyer-journey acceptance is a standard release gate;
- legal-output golden sampling exists and is reviewed by a lawyer;
- security hardening is reviewed for broader browser exposure;
- per-user audit and credential lifecycle are stronger than operator-managed
  beta accounts;
- feedback/bug evidence reliably includes recent user-action context;
- provider failures, job failures, and advisory signals are monitored outside
  the app UI;
- the architecture decision for public hosting, object storage, background
  workers, and durable tenant isolation is explicit.

## Bottom Line

I would be comfortable with a narrow, watched beta after a fresh current-commit
closeout and one true lawyer-journey drill. I would not widen access yet. The
app is past "can the screens load?" but not yet past "can the whole legal
workflow be repeatedly proved under beta conditions?"
