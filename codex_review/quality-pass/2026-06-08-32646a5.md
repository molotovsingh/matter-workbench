## Evidence And Fixes

### P1 - Runtime DB add-files allocation can race

The filesystem add-files path has an explicit per-matter queue. `services/upload-service.mjs:104-145`
wraps filesystem add-files in `withMatterWriteQueue`, and the queue itself is at
`services/upload-service.mjs:151-160`. That behavior is covered by the concurrent
filesystem test at `test/upload-api.test.mjs:105-170`, which asserts only one
intake allocation is in flight and that the two requests receive distinct
`INTAKE-02` / `INTAKE-03` and `FILE-0002` / `FILE-0003`.

The runtime DB path bypasses that queue at `services/upload-service.mjs:89-101`
and calls `runtimeDbStorageService.addUploadedFilesToMatter`. Inside that service,
the allocation state is read before the write transaction:
`services/runtime-db-storage-service.mjs:243-257` reads `nextIntakeNumber` and
`matter.nextFileNumber`; `services/runtime-db-storage-service.mjs:718-756`
builds that state query without `FOR UPDATE`; `services/runtime-db-storage-service.mjs:1298-1311`
later updates `matters.next_file_number` with `greatest(...)`.

The schema makes duplicate file allocation a hard data-integrity issue:
`db/migrations/001_control_plane.sql:92-109` has unique constraints on
`(matter_id, file_number)` and `(matter_id, file_id)`. The database already has a
row-locking allocator, `allocate_matter_file_number`, at
`db/migrations/001_control_plane.sql:491-515`, but this runtime upload path does
not use it. The existing runtime add-upload test,
`test/runtime-db-storage-service.test.mjs:444-484`, covers one append and checks
the generated SQL, but it does not simulate two interleaved appends.

Impact: two add-files requests to the same runtime DB matter can both read the
same `next_file_number` and intake number, generate the same deterministic
intake/upload/import IDs, and attempt the same `FILE-xxxx` identifiers. The best
case is one request fails on uniqueness. The worse case is an idempotency-key or
upsert collision silently points a later upload at a previous intake identity.

Concrete fix:

1. Move intake and file-number allocation into the same DB write transaction.
2. Lock the target matter row with `SELECT ... FOR UPDATE`, or call
   `allocate_matter_file_number` for each file while the transaction is open.
3. Compute the next intake number inside that lock, or add a dedicated locked
   intake allocator.
4. Add a runtime DB concurrency regression mirroring
   `test/upload-api.test.mjs:105-170`, with a fake spawn that proves the
   generated SQL uses a locked allocation path.

### P2 - Materialized runtime DB writes do not represent deletes

`runMaterializedMatterWrite` materializes the DB workspace, records initial
hashes for those paths, runs a filesystem-style operation, then persists only
files that still exist and whose hash changed. The relevant logic is
`services/runtime-db-storage-service.mjs:448-486`: initial hashes are captured at
`464-467`, current files are listed at `469`, changed files are accumulated at
`470-482`, and only those changed files are passed to `persistMaterializedFiles`
at `484-486`.

There is no comparison for "path existed before but is missing now." The storage
schema is ready for lifecycle states, including `deleted_pending` and `deleted`,
at `db/migrations/005_storage_object_lifecycle.sql:14-16`. The current tests
prove create/update persistence, for example the new-artifact test at
`test/runtime-db-storage-service.test.mjs:297-315`, but I did not find a
runtime DB materialized-write test that removes an artifact and expects a
tombstone/update in SQL.

Impact: this is not a confirmed break in the most common user path because I did
not find a main workflow that routinely deletes matter artifacts. It is still a
hosted-beta correctness gap: any future cleanup, repair, regeneration, or
doctor-style operation that deletes a stale materialized file will leave the DB
workspace showing an artifact that no longer exists in the filesystem truth the
operation produced.

Concrete fix:

1. Track `deletedPaths = initialPaths - currentPaths` after the operation.
2. For each deleted path, update the matching `storage_objects` row to
   `deleted_pending` or `deleted` and update role-specific rows as needed.
3. Add a regression where the operation removes a materialized file and the
   generated SQL contains the lifecycle update.

### P2 - Intake and extraction write durability is inconsistent

The repo has a good atomic-write primitive:
`shared/atomic-file.mjs:5-16` writes to a unique temp file and renames it into
place, and `services/json-store-persistence.mjs:7-31` layers a mutation queue and
atomic JSON writes over that primitive. Some newer workflow artifacts already
use it: Source Index writes atomically at `source-descriptors-engine.mjs:84-89`,
and List of Dates JSON/CSV/Markdown writes through `writeFileAtomic` in
`listofdates/artifacts.mjs:58-110`.

The two older core engines still write critical matter artifacts directly.
`matter-init-engine.mjs:399-409` writes the intake log, file register, and
`matter.json` with direct `writeFile` calls. `extract-engine.mjs:212-217` writes
the extraction log directly, and `extract-engine.mjs:369-371` writes extraction
records and flat text directly.

Impact: a crash, killed process, disk interruption, or failed write at the wrong
time can leave the repo's most important matter artifacts truncated or partially
written. That risk is not hypothetical at the architecture level: the codebase
already created and adopted an atomic helper for similar JSON stores and newer
artifacts.

Concrete fix:

1. Replace direct critical artifact writes in `matter-init-engine.mjs` and
   `extract-engine.mjs` with `writeFileAtomic`.
2. Keep the ordinary file copies as they are; the concern is structured state
   artifacts such as `matter.json`, register/log CSVs, extraction JSON, and
   extracted text outputs.
3. Add targeted forced-rename/write-failure tests similar in spirit to
   `test/json-store-persistence.test.mjs`, proving a failed atomic write does
   not corrupt the prior artifact.

### P2 - Runtime DB configurable skill catalog has no DB-level concurrency guard

The filesystem skill catalog uses the shared mutation queue:
`services/configurable-skill-store.mjs:39-45` calls
`persistence.withStoreMutation`, which serializes read/mutate/write inside one
process.

The runtime DB skill store has the same read/mutate/write shape but without a
DB-level lock or compare-and-swap. `services/runtime-db-configurable-skill-store.mjs:40-47`
reads the full store, lets the caller mutate it, and writes the store. The writer
then upserts every skill passed to it at
`services/runtime-db-configurable-skill-store.mjs:28-37` and
`services/runtime-db-configurable-skill-store.mjs:124-151`. The callers include
skill creation at `services/configurable-skills-service.mjs:98-120` and
lifecycle changes at `services/configurable-skills-service.mjs:267-312`.

Impact: two hosted sessions can both read the catalog, apply different lifecycle
or creation changes, and then write their snapshots. Because the runtime store
does not lock rows or check `updated_at`/version preconditions, the later write
can overwrite status metadata from the earlier one. The risk is higher in
hosted mode than in the local filesystem mode because multiple processes or
operators are plausible.

Concrete fix:

1. Replace full-store lifecycle updates with row-level SQL operations for the
   affected skill.
2. For create/version operations, use a transaction with row locks or optimistic
   version checks.
3. Add an interleaving regression that simulates two `updateStore` calls based
   on the same starting rows and proves one cannot silently overwrite the other.

## Themes

1. Hosted-mode invariants need the same strength as filesystem-mode invariants.
   Filesystem add-files and skill stores have local serialization; runtime DB
   add-files and the runtime skill catalog need database locks or optimistic
   versioning because hosted mode can have concurrent actors.
2. The materialized runtime DB bridge currently models "write files" better than
   "reconcile a workspace." Create/update paths are well covered, but delete
   lifecycle is not represented yet.
3. Write durability is uneven. Newer JSON stores, source descriptors, and
   list-of-dates artifacts use the atomic helper; the older intake and
   extraction engines still write critical structured artifacts directly.

## Highest-Leverage Fixes

1. Fix runtime DB add-files allocation first. It is the only P1 because it can
   corrupt or fail a real hosted user flow under normal concurrent use.
2. Add delete reconciliation to `runMaterializedMatterWrite` before adding more
   repair/cleanup workflows to hosted mode.
3. Convert core intake/extraction structured artifact writes to
   `writeFileAtomic` and add forced-failure regression coverage.
4. Replace runtime DB configurable skill full-store updates with row-scoped
   transactional updates or optimistic version checks.
