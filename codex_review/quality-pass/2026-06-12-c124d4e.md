## Evidence And Fixes

### P2 - Rollback's default deployment root targets a literal `$HOME`

`scripts/private-vm-rollback.mjs` defaults `deploymentRoot` to `"$HOME/matter-workbench-deployments"` in the parser and plan (`scripts/private-vm-rollback.mjs:9`, `scripts/private-vm-rollback.mjs:13`, `scripts/private-vm-rollback.mjs:61`, `scripts/private-vm-rollback.mjs:75`). The generated remote preflight shell-quotes `appDir`, so the VM sees a literal `'$HOME/matter-workbench-deployments/<release>/app'` instead of expanding `$HOME` (`scripts/private-vm-rollback.mjs:87`, `scripts/private-vm-rollback.mjs:91`).

The deploy script already solved this differently: when `--user aks` is supplied, deploy defaults to `/home/aks/matter-workbench-deployments` (`scripts/private-vm-rsync-deploy.mjs:85`, `scripts/private-vm-rsync-deploy.mjs:383`). Rollback tests cover explicit `--deployment-root` only, so the default path mismatch is not exercised (`test/private-vm-rollback.test.mjs:44`, `test/private-vm-rollback.test.mjs:50`, `test/private-vm-rollback.test.mjs:59`).

One-off proof: parsing rollback args with `--host vm.example.test --user aks --to abc1234` produced `deploymentRoot: "$HOME/matter-workbench-deployments"` and a preflight command containing `test -d '$HOME/matter-workbench-deployments/abc1234/app'`.

Fix: share the deploy script's remote-root resolver with rollback, or make rollback default to an empty root and resolve `/home/<user>/matter-workbench-deployments` after parsing. Add a regression test that omits `--deployment-root` with `user: "aks"` and asserts no `$HOME/matter-workbench-deployments` remains in the plan.

### P2 - Runtime DB materialization trusts persisted object keys as filesystem paths

Runtime DB workspace rows come from `storage_objects.object_key` (`services/runtime-db-storage-service.mjs:662`, `services/runtime-db-storage-service.mjs:672`, `services/runtime-db-storage-service.mjs:699`). `buildWorkspaceTree` converts those keys into `relativePath` via `relativePathFromObjectKey` and splits the result into path parts without rejecting `..` (`services/runtime-db-storage-service.mjs:596`, `services/runtime-db-storage-service.mjs:607`, `services/runtime-db-storage-service.mjs:609`). That path later gets joined under a temporary matter root during materialization (`services/runtime-db-storage-service.mjs:526`, `services/runtime-db-storage-service.mjs:535`).

The same pattern exists in the upload-intake path that rematerializes existing DB payload files before calling `runMatterInit`: `writeExistingPayloadFilesToMatterRoot` normalizes the object path but does not validate path segments before `path.join` (`services/runtime-db-storage-service.mjs:1388`, `services/runtime-db-storage-service.mjs:1390`, `services/runtime-db-storage-service.mjs:1392`). By contrast, freshly uploaded relative paths do use `validateRelativePath` (`services/runtime-db-storage-service.mjs:1408`; `shared/safe-paths.mjs:35`).

One-off proof: a simulated DB row with object key `DB Matter/../escape.txt` caused `runMaterializedMatterRead` to write `escape.txt` outside the temporary matter root before cleanup returned `escaped: true`.

Why this is P2 rather than P1: normal product upload paths are validated, and the focused runtime DB tests pass. The fragile boundary is the DB custody ledger itself. If a legacy import, migration, manual repair, or future ingestion path writes an unsafe `object_key`, materialization trusts it.

Fix: validate every DB-derived relative path at the boundary. The narrow repair is to run `validateRelativePath(relativePathFromObjectKey(...))` before adding nodes to `buildWorkspaceTree` and before writing existing payloads. Bad custody rows should be skipped with structured evidence or fail closed with a 409, not materialized. Add a regression test with `DB Matter/../escape.txt`.

### P2 - Deploy release labels can drift from the synced tree

`scripts/private-vm-rsync-deploy.mjs` accepts `--commit` directly (`scripts/private-vm-rsync-deploy.mjs:56`) and `runPrivateVmRsyncDeploy` uses that provided string without resolving HEAD (`scripts/private-vm-rsync-deploy.mjs:281`, `scripts/private-vm-rsync-deploy.mjs:290`). The rsync step then sends the current checked-out tracked files using `git ls-files -z`, not the tree object for the supplied commit (`scripts/private-vm-rsync-deploy.mjs:137`, `scripts/private-vm-rsync-deploy.mjs:143`, `scripts/private-vm-rsync-deploy.mjs:145`, `scripts/private-vm-rsync-deploy.mjs:152`).

The dirty-worktree guard catches uncommitted tracked changes in live deploys (`scripts/private-vm-rsync-deploy.mjs:282`), but it does not prove that a user-provided `--commit` equals the checked-out commit. A dry-run proof with `commit: "operator-label"` and a resolver that would have returned `"actual-head"` generated a release directory ending in `/operator-label` while still rsyncing the current source directory.

Fix: always resolve the checked-out HEAD, then reject a supplied `--commit` that does not match the short or full HEAD. If an operator really needs a human label, add a separate `--release-label` field and keep `commit` mechanically derived.

## Themes

1. Deployment tooling is close to operator-grade but still has two naming/traceability traps. Rollback and deploy both protect secrets and support dry-run plans, but they need stricter shared semantics for "where is a release" and "what exact code is this release."

2. Runtime DB mode is now the main product boundary. The code correctly validates fresh user-uploaded paths, but DB custody metadata also needs to be treated as untrusted input because it drives temporary filesystem materialization.

3. The private-beta access model is becoming consistent across layers. The best recent changes connect server-side filters, React visibility, runtime DB ownership, and tests. Keep adding safeguards at the shared route/service level first; UI hiding should remain the second layer, not the boundary.

## Highest-Leverage Fixes

1. Fix rollback default root resolution and add the missing no-`--deployment-root` test. This is the quickest operational win and prevents a bad rollback drill.

2. Add one DB-object-key validation helper and use it in workspace-tree building, existing-payload materialization, materialized write/read, and status advice. Then add the `../escape.txt` regression test.

3. Split deploy's release label from commit identity. Resolve HEAD every time, fail on mismatch, and keep a separate optional label only if operators need one.
