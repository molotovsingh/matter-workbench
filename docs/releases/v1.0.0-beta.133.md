## What this release is

**Fast extraction is prepared to become available to testers.** Both halves ship together at activation: the code that makes V4's output reach a matter record, and the evidence-gated configuration that turns V4 on. The database is now provisioned and proven recoverable, but the flag is still absent.

An earlier draft of this note described shipping V4 to the VM *dormant*. That deploy has already happened, on 2026-08-28, and is recorded as a **Tier 2 maintenance checkpoint** at `34de07b` — correctly, because with the flag unset no tester could perceive it. That left no tester-visible event for a dormant release to announce, so this number is now spent on the change testers can actually see.

## Why This Is Tier 1

Any one of these would be sufficient under `docs/release-policy.md`:

- **User-visible behaviour** — the fast-extraction panel appears in Add Files, and reports which documents entered the matter record.
- **Storage, custody, and preparation semantics** — extraction results now enter the matter record, and preparation skips its own slow OCR for those documents.
- **Runtime DB migration** — `010_intake_filing_summary.sql` adds a column to the V4 intake table on first boot.
- **New deployment posture** — V4 stops being inert on this deployment.

## Included Since v1.0.0-beta.132

`v1.0.0-beta.132` was tagged at `1647f3c`, but the VM has been running `5cf4447` and then `34de07b`. Everything below is measured against the beta.132 **tag**, so it includes work already live but never named in a release.

**Fast extraction reaches the matter record.**

- Extraction results are filed into the matter under either storage arrangement. Previously the filing step was disabled whenever matters were held in the runtime database, which is this deployment's configuration — so results were produced correctly and then went nowhere.
- Filing rules and storage access are separated by a storage port with one adapter per arrangement, so the rules protecting the legal record exist in one place rather than being written twice.
- Filing declines to write into a matter outside the caller's tenant.
- The panel reports what entered the record and what did not, with a reason for each, and rejoins a run after a reload or navigating away — runs reach several minutes on large documents.

**V4 document intake and extraction, provisioned but not yet enabled.**

- A complete isolated intake/extraction vertical: versioned HTTP boundary, PostgreSQL control plane, immutable custody, fenced document-local OCR ranges, durable work graph, selective repair with lineage, signed result events, and fenced outbox delivery.
- A provider ladder with pinned adapters — Mistral OCR 4.1 primary, Gemini 3.7 range and page repair, GPT-5.4 apex rung — with dynamic lane discovery, admission backpressure, and evidence-sized hang-detection timeouts.
- A native-text fast lane that reads born-digital pages without paying for OCR.
- A local content-addressed blob cache, so a document's work units stop re-downloading the whole source per unit.

**Legacy-path changes live since before this release but never named in one.**

- Matter preparation shows elapsed time.
- Large-upload guidance clarified, and deploys are guarded while processing is in flight.
- Posture diagnosis is recorded as unconfirmed by the user, with explicit approve/reject controls.
- Preparation polling recovery and runtime story/retry persistence seams closed.

## Not Promised

- This remains a supervised private beta, not a production-readiness claim.
- **V4 is enabled, not certified.** All five acceptance gates — `V4-LOAD-001`, `V4-QUALITY-001`, `V4-QUOTA-001`, `V4-SECURITY-001`, `V4-CUTOVER-001` — remain open. Making results reach the matter record does not bear on any of them.
- **The V4 cutover is not authorized and is not performed.** Legacy extraction remains the authoritative path, and `docs/operations/document-intake-extraction-v4-cutover.md` still reads "not authorized".
- **Fast extraction is not automatic.** It remains an explicit choice when adding documents to an existing matter. Creating a new matter does not use it, and no automated preparation sequence invokes it.
- **The latency SLO is not met by preliminary evidence.** Ordinary briefs of 6–33 pages completed in 26–88 seconds, but 300+ page archival documents took 6–8 minutes, and every preliminary run missed the envelope target. No certification run has been performed.
- **Provider quota is uncertified.** No lane has demonstrated administrative quota from a production identity.
- **Independent security review has not been performed.**
- **Passage references are not interchangeable across extraction paths.** Fast and normal extraction divide a page into passages differently, so a citation can mean different things depending on which produced the record. This is a real defect; it predates this release, affects both storage arrangements identically, and needs a citation resolver that does not exist yet.
- **Concurrent extraction of the same document by both paths is unchanged.** The existing race is inherited deliberately.
- **The outcome report is not archived.** It lives with the run and is discarded with it. What was filed remains visible in the matter's activity log regardless.

## Operator Notes

- V4 stays dormant unless `MWB_V4_INTAKE=1` is set in `runtime.env`. Deploying this release without that flag changes nothing a tester can see.
- Enabling it also needs `MWB_V4_DB_URL` and provider keys. `MWB_V4_DB_POOL_MAX` must remain `16`, and `MWB_V4_AUTO_MIGRATE` must remain `0`; all 11 migrations were applied out of band while the flag was off.
- No object-storage configuration is present on this VM, so V4 uses local-disk object storage under `MWB_V4_STORE_ROOT`. That is deliberate here: it removes the data-residency question entirely, and the volume has ample free space after the 2026-08-28 deployment prune.
- The VM has 3.8 GB of RAM. Start `MWB_V4_LANES` around 4 — well below the 24 lanes used in load evidence, which was gathered on larger hardware.
- **Immediate rollback target: `34de07b`** — the commit running before this release. **Not** the beta.132 tag target `1647f3c`, which is eleven commits behind the VM and would silently remove live tester-visible behaviour. See the 2026-08-28 entry in `docs/releases/maintenance-checkpoints.md`.
- Use `npm run private-vm:rollback -- --to <commit>`; do not move release tags.
- To disable V4 without rolling back, run `npm run v4:db:disable`. It atomically removes only `MWB_V4_INTAKE`, then restarts; the V4 database and matters already filed remain intact.
