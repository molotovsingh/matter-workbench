## Why This Is Tier 1

Four independent triggers from the release policy, any one of which would be sufficient:

- **New deployment posture** — V4 executable source ships to the beta VM for the first time.
- **Storage, custody, and upload semantics** — V4 introduces a separate intake path with its own PostgreSQL schema, object-storage custody model, and upload authorization.
- **Runtime DB migrations** — the V4 schema migrates on first boot.
- **User-visible behavior** — the workbench probes the mount's `/status` endpoint and renders the V4 fast-extraction panel once it stops returning 404.

## Included Since v1.0.0-beta.132

This release carries roughly six weeks of work that has been accumulating on `main` since 2026-07-16.

**V4 document intake and extraction (flag-gated, off by default).**

- A complete isolated intake/extraction vertical: versioned HTTP boundary, PostgreSQL control plane, S3-compatible immutable custody, fenced document-local OCR ranges, durable work graph, selective repair with lineage, signed result events, and fenced outbox delivery.
- A provider ladder with pinned adapters — Mistral OCR 4.1 primary, Gemini 3.7 range and page repair, GPT-5.4 apex rung — with dynamic lane discovery, admission backpressure, and evidence-sized hang-detection timeouts.
- A native-text fast lane that reads born-digital pages without paying for OCR.
- Predictive burst capacity, tenant-scoped calibration, live progress and ETA projection.
- A local content-addressed blob cache so a document's work units stop re-downloading the whole source per unit.
- A result bridge that files ready V4 output into the legacy matter record as cached extract-stage output, so preparation skips its own slow OCR for those files.
- Flag-gated workbench panel: nothing mounts and nothing renders unless `MWB_V4_INTAKE=1`.

**Legacy path changes that have been undeployed since beta.132.**

- Matter preparation shows elapsed time.
- Large-upload guidance clarified, and deploys are guarded while processing is in flight.
- Posture diagnosis is recorded as unconfirmed by the user, with explicit approve/reject controls.
- Preparation polling recovery and runtime story/retry persistence seams closed.

**Research and evidence (not user-facing).** v2/v3 extraction benchmarks, PDFEval Gold30 reference, and the V4 certification tooling for load, quality, quota, security, and cutover.

## Not Promised

- This remains a supervised private beta, not a production-readiness claim.
- **V4 is shipped, not certified.** Five acceptance gates remain open on evidence: `V4-LOAD-001`, `V4-QUALITY-001`, `V4-QUOTA-001`, `V4-SECURITY-001`, and `V4-CUTOVER-001`. Shipping the code to the VM does not close any of them.
- **The V4 cutover is not authorized and is not performed by this release.** Legacy intake remains the authoritative path. `docs/operations/document-intake-extraction-v4-cutover.md` still reads "not authorized," and the cutover it describes is one-way with no dual-write and no fallback.
- The V4 latency SLO (P95 60s, P99 120s) is **not** met by preliminary evidence. Ordinary briefs of 6–33 pages completed in 26–88 seconds, but 300+ page archival documents took 6–8 minutes, and every preliminary run missed the envelope target. No certification run has been performed.
- Provider quota is uncertified. No lane has demonstrated administrative quota from a production identity, and the Mistral production workspace and Google billed project remain unidentified.
- Independent security review has not been performed. Automated evidence covers tenant RLS, TLS, versioned staging, leases, bounded scratch, and error redaction; it does not establish production bucket policy, KMS, regional residency, backup/PITR, network egress policy, identity rotation, retention, or penetration posture.
- V4 isolation is now **runtime-only**. Prior releases withheld V4 source from the VM entirely; this release ships it and relies on the flag alone. Flag off means no V4 module is loaded.
- An intake orphaned between custody commit and inspection cannot be healed through the API — upload tokens are client-held by design, so completion requires a fresh intake. Content-level dedup makes the re-upload cheap.

## Operator Notes

- V4 stays dormant unless `MWB_V4_INTAKE=1` is set in `runtime.env`. Deploying this release without that flag is a no-op for V4 and changes only the legacy-path items listed above.
- Enabling V4 additionally requires `MWB_V4_DB_URL`, the Spaces endpoint/region/bucket/keys, and provider keys. Use the Mumbai bucket, not sfo3: residency is a security-certification control, and the cross-continent round trip inflates every latency number you would collect.
- Set `MWB_V4_AUTO_MIGRATE` for the first boot so the V4 schema is created, then unset it.
- Immediate rollback target: `1647f3c` (`v1.0.0-beta.132` deployment checkpoint).
- Use `npm run private-vm:rollback -- --to <commit>` with the normal VM host/user options; do not move release tags.
- To disable V4 without rolling back, unset `MWB_V4_INTAKE` and restart. The mount is the only thing that goes away.
