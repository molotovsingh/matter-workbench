A repeatable engineering-quality review of the services that power the app.
(Git-ignored working doc in `claude_tests/`.)

This is **not** a formal security/correctness audit — it is a recurring
architecture-quality pass that asks one question per service: *is the problem
solved at the right level, and where is the risk?* It is good at spotting
patterns, weak seams, and refactor candidates. Three layers:

1. **[Review rubric](#review-rubric-the-template)** — the stable template + controlled vocabulary. Fill this in for each service.
2. **[Audit view](#audit-view)** — the scannable, severity-sorted result (what to fix first).
3. **[Evidence & fixes](#evidence--fixes-per-service)** — per-service `file:line` + the concrete fix, for a human or an agent.
4. **[Emerging themes](#emerging-themes)** — the cross-cutting payoff: where risk actually concentrates.

## Mental model

Matter Workbench turns a messy pile of case documents (a **"matter"** = one legal
case folder) into organized, labeled, chronology-ready legal work product.

The core loop is an assembly line:

```
raw documents → set up → extract text → label each doc → build a timeline → review
              (matter-init) (extract)  (describe-sources) (create-listofdates)
```

How a click becomes work:

```
Browser (react-ui/)        ← what the lawyer sees
   │  HTTP /api/...
server.mjs                 ← front door; builds every service once
   │
routes/ (route-dispatcher) ← which handler answers this URL?
   │
services/ (67 modules)     ← the logic, one job each
   │
engines + storage          ← do the work; save to files (or Postgres)
```

## Review rubric (the template)

One row per service. Fill these fields using the controlled vocabularies — that
is what makes the pass repeatable and comparable across runs.

| Field | Meaning | Allowed values |
|---|---|---|
| **service** | the module | `services/<name>.mjs` |
| **role** | what job it does for the product | free text (see Evidence table's *Problem / What it does*) |
| **storage mode** | how it behaves across the filesystem↔Postgres split | `filesystem` · `DB` (has a runtime-db twin or reads DB storage) · `bridge` (engine run via materialization) · `config` · `none` (stateless/AI) |
| **blast radius** | what the user loses if it's wrong | short phrase |
| **evidence** | exact anchors to verify the call | `file:line` (lives in the Evidence table) |
| **verdict** | the quality call | `right-sized` · `brittle` (fragile under change/scale/failure) · `overgrown` (too much in one place) · `risky` (security/data-integrity hazard). A trailing `*` = right-sized but with a minor warning. |
| **theme** | the cross-cutting pattern it instances | `DB seam` · `policy drift` · `mtime coupling` · `AI resilience` · `monolith` · `concurrency` · `secret-handling` · `decomposition+` (positive) · `—` (clean) |
| **action** | what to do about it | `ignore` · `watch` · `refactor` · `test now` |
| **severity** | how urgent | `P0` blocking now · `P1` fix before hosted cutover / correctness / security · `P2` minor, refactor when convenient · `P3` clean / cosmetic |

### Running the pass again

1. For each service, read it **plus its twin/siblings** (the DB twin, the shared helpers).
2. Fill the row using the vocab above; put exact `file:line` evidence + a one-line **Fix** in the Evidence table.
3. Tag the theme. If a genuinely new cross-cutting pattern appears, add it to [Emerging themes](#emerging-themes) as the next `T#`.
4. Re-sort the Audit view by severity; the **P1 queue** is the work list.

**Cadence:** re-run on a structural change — a new engine, the DB runtime cutover, a new storage mode, or a new AI surface. Diff the Audit view against the last run; new `P1/P2` rows are the regression signal.

## Emerging themes

Cross-cutting patterns that recur across services. The **Theme** column tags each
reviewed row with the ones it best illustrates (positive or negative). **All 28
core services reviewed.**

**Scoreboard.** ~20 of 28 are clean or near-clean (✅ / ✅ + minor). 8 carry a
real warning, and they are not scattered — they cluster:

- **5 on the filesystem↔Postgres seam (T1):** matter-store · workspace-service ·
  upload-service · matter-status · matter-rerun-advice.
- **2 on the two *paid* AI engines:** source-descriptors (T2 resilience) ·
  create-listofdates (T3 monolith + T5 prose-regex).
- **1 security surface:** ai-settings (the API-key chokepoint).

Every other AI service (copilot, router, interview-planner) and the entire
Skill Factory came back clean. The warnings concentrate at exactly two
boundaries — the storage migration and the two paid AI engines — and almost
every seam warning traces back to **one missing abstraction** and **one root
cause** (see Highest-leverage fixes). The patterns:

- **T1 — Debt lives on the filesystem↔Postgres seam.** Every non-clean verdict so
  far sits exactly where the local-file world meets the Postgres world. It shows
  up three ways: as rerun cost (source-descriptors), as scattered in-file
  mode-branches + process-global state (matter-store), and as the same contract
  implemented twice and able to drift (workspace-service's preview policy
  duplicated in its `runtime-db-storage-service` twin). Pure single-mode code
  stays clean — the same fault line the DB-hardening review kept hitting.
  **Deepest form:** some logic is filesystem-coupled *by construction* —
  matter-rerun-advice decides staleness from file **mtimes**, which have no
  equivalent on DB rows, so the Postgres twin stubs it to "current" and the
  staleness/refresh feature silently vanishes in DB mode (the behavioral drift
  seen in matter-status). The fix is the same root cause: depend on the content
  hashes the artifacts already store, not the filesystem.
- **T2 — Trust ≠ resilience in AI engines.** Output-trust (citation grounding,
  server-owned identity, strict schema) and run-resilience (partial-persist,
  cache, retry) are independent axes. **Trust is a codebase-wide strength:** every
  AI call — source-descriptors, matter-copilot, skill-router, skill-interview-
  planner — uses a strict JSON schema with enums and grounds output in real
  source citations, and the server clamps/owns the trust-critical fields. The gap
  is purely *resilience*, and only in the two **paid batch** engines:
  source-descriptors discards already-paid batches on a late failure and never
  caches. Single-call AI services (copilot, router, planner) have no such risk.
  So the rule: nailing trust does not buy resilience — and only batched/paid work
  needs the resilience kit.
- **T3 — The failure mode is under-abstraction, not over-engineering.** The
  warnings are about code that is too flat for the realities it now serves —
  god-functions, scattered mode-branches, monoliths — never gratuitous layering.
  The codebase errs toward flat: the safer direction, but it has real costs once
  a second mode or scale arrives.
- **T4 — Decomposition discipline is strong — with one loud exception.** Clean
  module decomposition is the *norm* here: extract (engine + 13 format/OCR utils),
  the whole Skill Factory (~10 `configurable-skill-*` modules behind a thin
  orchestrator), matter-context (packet/preview/search), matter-attention (one
  builder per source). The lone outlier is create-listofdates — a 1497-line
  monolith doing the same "complex AI feature" job the Skill Factory does cleanly.
  So COD isn't how the team works; it's the one place they didn't, and
  configurable-skills-service is the ready-made template to fix it.
- **T5 — Don't police LLM prose in post-processing.** create-listofdates rewrites
  the model's legal language with hardcoded regexes (one tuned to a specific eval
  matter). That is a maintenance treadmill and overfits eval data; the right
  layer is the prompt plus source-grounded checks.

- **T6 — Concurrency discipline is real but applied unevenly.** The codebase
  *has* a serialization primitive and uses it well: the JSON-store layer wraps
  every mutation in `withStoreMutation` (skill-ideas/samples/runs), the audit log
  serializes writes through an append-queue, and skill-samples even allocates
  version numbers collision-free *inside* the lock. Yet the matter layer skips it
  — upload-service's `FILE-NNNN`/intake-number is an unguarded read-then-write,
  and matter-store keeps a process-global active matter. The team clearly knows
  how to serialize; they just didn't at the matter-allocation seam. Local-safe
  today, hosted-unsafe — and the fix already exists in-repo (copy the
  skill-samples pattern).

### What the codebase does consistently well

Worth naming, because the warnings above are the exception, not the rule:

- **Citation grounding & server-owned identity** — AI output must cite real
  source blocks; the server, not the model, owns sha256/labels (source-descriptors,
  matter-copilot, create-listofdates).
- **Schema-validated AI** — every model call uses strict JSON schema + enums;
  outputs are constrained classifications, not free text.
- **Graceful degradation** — read/status services catch and return safe defaults
  instead of throwing into the UI (matter-status, prepare-matter, context).
- **Atomic writes** (`writeFileAtomic`) and **path safety** (`validateMatterName`
  + `isInsideRoot` + blocked-path policy) on every file path from HTTP.
- **Cost-awareness** — `RUN` vs `CONFIRM_PAID_RUN`, the free label-refresh path,
  and bounded AI context limits.

### Highest-leverage fixes

The 8 warnings collapse into a short list of root causes — fix these and most of
the table goes green:

1. **One storage adapter boundary** (`MatterStore` / `MatterWriteStore` interface
   with filesystem + runtime-DB implementations). Collapses T1's scattered
   in-method forks (matter-store, upload-service) and duplicated contracts
   (workspace preview policy, the two `readMatterStatus`). One seam instead of N.
2. **Content-hash dependency tracking** (replace mtime staleness). Fixes
   matter-rerun-advice correctness *and* makes staleness portable to Postgres,
   closing the matter-status behavioral drift — one change, three warnings.
3. **Paid-AI resilience kit** — per-batch persist/cache + quarantine-don't-throw +
   wider retry for source-descriptors; and split create-listofdates using the
   Skill Factory as the template, moving conclusion-control into the prompt.
4. **Apply the in-repo concurrency primitive uniformly** — serialize
   `FILE-NNNN`/intake allocation the way the skill stores already do (T6).

### Meta-observation

Deterministic, single-mode core logic is consistently clean; **100% of warnings
sit at one of two boundaries** — the filesystem↔Postgres migration or the two
paid AI engines (plus one isolated secret-handling surface). Risk concentrates at
seams, not in the core. The migration debt in particular is *shallow but
repeated*: it looks like many problems but is really one missing abstraction and
one filesystem-coupled signal, felt in five places.

## Legend

- ✅ = has a dedicated `runtime-db-*` twin that serves the same job from Postgres
  when cutover flags are on.
- "reads DB in storage mode" = no separate twin; the existing service reads from
  `runtime-db-storage-service` when Postgres mode is active.
- ¹ **via bridge** = the engine isn't DB-native; in Postgres mode
  [runtime-db-storage-service.mjs](../services/runtime-db-storage-service.mjs)
  reconstructs a temp folder, runs the engine, and writes results back to the DB
  (the "materialization bridge").
- ² Matter Attention is a *projection* — it reads facts from jobs/validations/
  incidents rather than being its own source of truth.

### How to read the Verdict column

One dimension per service: **is the problem solved at the right level, or
over/under-engineered?** Each verdict is dual-audience —

- **marker:** ✅ right-sized · ⚠️ has a warning · 🔻 under-decomposed · ⏳ not yet reviewed
- **judgment + reasoning:** plain words, so a human knows *why*.
- **`file:line` + Fix:** so an agent can open the spot and change it.

## The one big idea: two storage worlds

- **Default world (today):** everything lives in **local files** — the matter
  folder for documents, root-level `*.json` files for skills/config.
- **Postgres world (in progress):** the `runtime-db-*` services serve the *same*
  app from a database, switched on by `MWB_RUNTIME_DB=postgres` + approval flags.
  The DB review work (atomicity, superuser guard, payload custody) is about
  making that second world safe enough to trust.
