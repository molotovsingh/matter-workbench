### New P2 (1) — the fix that forked a contract

**F1b — `configurable-skill-store.mjs:39-46` (filesystem twin): `updateStore` still writes the pre-mutation store; the two twins now disagree about the mutator contract.**

The F1 fix landed only in the runtime-db twin. The filesystem twin — selected whenever runtime-db mode is off, via the fallback at `configurable-skills-service.mjs:73` (`skillStore || createConfigurableSkillStore(…)`), i.e. **the default local mode** — still does:

```js
const store = await readStore();
const result = await mutator(store);
await writeStore(store);          // pre-mutation object, return value ignored
```

A mutator that returns a replacement store now **works in DB mode and silently no-ops in filesystem mode**. Today this is latent — both live mutators (`configurable-skills-service.mjs:104`, `:273`) mutate `store` in place (`configurable-skill-creation-pipeline.mjs:99` does `store.skills.push(draft)`) — but the new DB-twin test *enshrines* the replacement contract, making it likely the next mutator author relies on it and ships a change that vanishes in filesystem mode with no error.

**Fix:** Mirror the guard in the filesystem twin — change `configurable-skill-store.mjs:43` to `await writeStore(isStoreReplacement(result) ? result : store);` and move `isStoreReplacement` to a shared module (e.g. `configurable-skill-definition.mjs`) so the contract is defined once. Add the same replacement-mutator test for this twin.

### New P3 (1)

**`private-vm-rsync-deploy.mjs:94,247` — the broken `"$HOME/matter-workbench-deployments"` literal survives as default parameter values.** Commit `30c0a37` correctly diagnosed that the old default could never work — `deploymentRoot` is always passed through `shellQuote()` (`:125-126,181,184`), so the remote shell receives `'$HOME/…'` single-quoted and never expands it. The parser now resolves a real path (`defaultRemoteDeploymentRoot`, `:362-367`, with test coverage). But the same broken literal remains as the default for `buildPrivateVmRsyncDeployPlan` (`:94`) and `runPrivateVmRsyncDeploy` (`:247`), and as the empty-user fallback inside `defaultRemoteDeploymentRoot` itself (`:366`). A programmatic caller that omits `deploymentRoot` gets a preflight failure (`test -d '$HOME/…'` — fails closed, no damage) with a confusing error. **Fix:** delete the literal defaults; have both functions throw "deploymentRoot is required" when missing, and make the empty-user branch throw rather than return a value that cannot work.
