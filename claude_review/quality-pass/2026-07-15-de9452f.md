## New findings

### P1 — fix before the next milestone

**R11-1 — DB source removal fabricates custody events and clobbers currentness when the document is already inactive; the twins disagree (P1, risky, T7×T14).**
`services/source-removal-mutation-service.mjs:246-249` — `selected_document` is `updated_document UNION ALL target_document WHERE NOT EXISTS (updated_document)`, i.e. non-empty whenever the document *exists*, not whenever it *transitioned*. `inserted_event` (`:250-272`) joins it unconditionally, and `upserted_currentness` gates on it (`:316`). The client mints a fresh idempotency key per invocation (`react-ui/src/components/layout/MainContent.tsx:293-296`, `Date.now()+random`), so `on conflict do nothing` never suppresses a replay. Consequence: a second removal attempt on an already-inactive document **inserts another `source_file.removed_from_active_record` event** (payload `previous_status: 'removed_from_active_record'` — fabricated history in a legal custody ledger) and **overwrites currentness rows** (possibly clobbering newer states), while the JSON result simultaneously reports `state: 'already_inactive'`. The filesystem twin correctly early-returns with no event and no currentness write (`:78-87`). Found independently by two reviewers; re-verified in the SQL and the client key-generation by the lead. The DB twin is tested only by regex-over-SQL, which is exactly why this survived. **Fix:** gate `inserted_event`, the custom-skill branch of `artifact_candidates` (`:297`), and `upserted_currentness` on `exists (select 1 from updated_document)`; keep `selected_document` only for result-state computation. Add a real-Postgres (or executed-builder) test of the three states: removed / already_inactive / not_found.

**R11-2 — Write-queue key mismatch deserializes same-matter upload writes, reopening the R10-7 lost-intake race (P1, risky, T8).**
`services/runtime-db-storage-service.mjs:286` serializes `addUploadedFilesToMatter` under the **matter id**; `commitUploadSession` at `:498` queues under `upload-session:${sessionId}`. Two session commits to the same matter (two tabs, or a resumed stale session landing during a fresh upload), or a session commit racing a legacy add-files, now interleave freely — and both paths still do the R10-7 cross-transaction read-merge-write of `matter.json` (allocation txn → `readWorkspacePayloadFiles` `:598` → persist txn), so one intake vanishes from the manifest. R10-7's root cause was never fixed structurally; the in-process matter-keyed queue was the mitigation, and the new first-class path opted out of it. Compounding: `readUploadSessionForCommit` (`:808-813`) takes `FOR UPDATE` in a transaction that commits immediately — the lock guards nothing — and the commit UPDATE has no status predicate, so a `cancelUploadSession` (`:783-806`, also not routed through the queue) landing mid-commit is silently overwritten (cancel-vs-commit ends "committed"). Verified by two reviewers + lead. **Fix:** derive the commit queue key from the matter (resolvable from the session before queuing); route cancel through the same queue; add `and status not in ('cancelled','failed')` to the commit UPDATE and assert the row count. Root cause: rebuild `matter.json` inside the persistence transaction from DB state (or hold a `pg_advisory_xact_lock(matter_id)` across read+merge+write).

## Emerging themes

- **T14 — sibling-path bypass (NEW, owns both P1s and five P2s).** The guard exists and is well-built; a *second* path through the same state skips it. Ask mode blocks invented citations — research mode doesn't (R11-19). The preparation queue enforces idempotency — inline skill runs don't (R11-5). Job reads are visibility-scoped — `retry()`'s job read isn't (R11-4). The FS removal twin no-ops on already-inactive — the DB twin doesn't (R11-1). Add-files commits are matter-serialized — session commits aren't (R11-2). Commit enqueues extract — commit-*retry* doesn't (R11-15). First-open signals ingest — recurrences don't (R11-9). This is T7's twin-drift generalized: the drift is no longer between storage modes but between the *first-pass path and the replay/retry/recurrence path*. **The review heuristic that pays: for every flow, ask "what happens the second time?"**

- **T7 — twin drift: the discipline is real, the perimeter keeps moving.** Cleared at the core again (auth-primitives extraction, shared event normalizers, injected reader/writer de-twinning in MW LOD and posture — one service body serving both storage modes is now the house pattern). Regrown at the edges: removal semantics (R11-1), preview-vs-mutation (R11-8), App/MatterOverview workflow duplication (R11-25), the dead-but-maintained legacy frontend (R11-26), three technical-file classifications (R11-27), CSV headers ×2, lifecycle vocab ×4, inactive-status vocab ×4.

- **T8 — write-path integrity: the single-transaction work is excellent; the multi-transaction seams are where it breaks.** The commit transaction itself is atomic and payload-hygienic; the removal DB mutation is one transaction with FOR UPDATE. But matter.json merge still spans transactions (R11-2), the commit lock evaporates before the work (cancel-vs-commit), enqueue rides outside the commit (R11-15), and matter creation is check-then-insert (R11-11).

- **T10 — string-tier tests: both P1s lived exactly where the tests are regex.** The DB removal SQL and the mothership lifecycle upsert are tested by regex-over-SQL/mocked `database.query` — neither can see a wrong join condition. The skill-runner retry test asserts the one field the runner doesn't use. Meanwhile the *good* tier expanded: transpile-and-execute React lib tests, the css-a11y test, the upload parity test (which even pins an import de-duplication), a true end-to-end error-boundary test. **The single highest-leverage test investment: a FS↔DB twin-parity harness that runs one scenario through both implementations and diffs results — it would have caught R11-1, the event-listing drift, and the custom-skill-output gap in one fixture.**

- **T9 — egress deadlines, client edition.** The server learned this lesson (every research/sidecar fetch has AbortController); react-ui hasn't — zero `AbortSignal` in the client, telemetry awaited between preparation stages (R11-18), `testConnection` and openai-direct `source_backed_analysis` unbounded.

**Meta-observation.** Run 10 said risk had migrated from cores to boundaries. Run 11 sharpens it: the boundaries are now specifically **temporal** — replay, retry, recurrence, resume, reopen. Idempotency is the axis this codebase's next quality plateau lives on.
