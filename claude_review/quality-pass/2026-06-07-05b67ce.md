### Active P1s (verified in current code)

#### `upload-service` — 🔻 brittle (P1, concurrency)

🔻 **FILE-NNNN allocation is non-atomic on the filesystem path.** `upload-service.mjs:105-107`:
```js
const intakeNumber = await matterStore.nextIntakeNumber(root);
const fileIdStart = await matterStore.nextFileIdStart(root);
const priorHashes = await matterStore.priorHashIndex(root);
```
Three separate `stat`/`readdir` calls; no mutex. Concurrent requests between `nextIntakeNumber` and the eventual `writeUploadedFiles` can produce duplicate `INTAKE-NN` or `FILE-NNNN` identifiers. The DB path in the same function (`runtimeDbStorageService.addUploadedFilesToMatter`) reads `state.nextIntakeNumber` inside a transaction and is safe.

`json-store-persistence.mjs:13-16` provides `withStoreMutation` (a promise-queue serializer) — it is used by `job-status-service` correctly but not plumbed into `matter-store-intakes`.

**Fix:** Wrap the read-modify-write at `upload-service.mjs:104-130` in a serialized operation: either extend `json-store-persistence` to cover the intake register, or add a per-matter promise-queue like the job-status service uses. The serialization pattern already exists in the codebase — apply it uniformly (T6).

#### `matter-rerun-advice-service` — ⚠️ brittle (P1, mtime coupling)

⚠️ **Staleness detection is mtime-based throughout.** `matter-rerun-advice-service.mjs:109-111`:
```js
!newest || input.mtimeMs > newest.mtimeMs ? input : newest
const stale = newestInput && newestInput.mtimeMs > target.mtimeMs + 1;
```
Also at lines 224, 254, 260, 269, 280-281 — every file check reads `stat().mtimeMs`. When matter data is served from Postgres, there are no files and therefore no mtimes. The `runtimeStatusInputs` function in `runtime-db-storage-service.mjs` (lines ~350+) builds a parallel staleness signal from DB metadata, but `matter-rerun-advice-service` itself is never called in DB mode (the route dispatches entirely to `runtimeDbStorageService`).

The residual risk is forward-compatibility: if the FS-mode rerun advice is ever needed in a mixed-mode or migration scenario, the mtime dependency will silently return wrong results (always "stale" or "current" depending on temp file mtimes). It also makes the staleness signal non-portable.

**Fix:** Replace `mtimeMs` comparisons with content-hash comparisons (sha256 of the source index / list-of-dates JSON). Hash-based staleness works in both storage modes and is deterministic across renames or copies. `runtime-db-storage-service.mjs` already computes sha256 for every object — the pattern exists.

### New surfaces (Run 3 revision)

#### `private-beta-feedback-service` — ⚠️ brittle (P2, store fragility)

⚠️ **`normalizeStore` calls `normalizeFeedback` on every item at load time, and `normalizeFeedback` throws on empty `tryingToDo`.** `private-beta-feedback-service.mjs:183`:
```
if (!tryingToDo) throw makeHttpError("What were you trying to do? is required", 400);
```
`normalizeStore` at line 241 maps every stored item through `normalizeFeedback`. Any ledger item with a missing or empty `tryingToDo` — from a manually created entry, a schema migration edge case, or a prior version — will cause `loadStore` to throw, making `createFeedback`, `listFeedback`, and `syncQueuedFeedback` all unavailable until the file is manually repaired.

The `serialize` callback also calls `normalizeStore`, so the write path has the same failure mode: a mutated store containing a bad item will fail to serialize, losing the mutation (all data is preserved, but the write is dropped).

Strengths: the service follows T5 and T6 correctly — `redactSecretLikeText` is applied at `lines 393-398`, and `withStoreMutation` serializes all writes at line 47. The `telemetryMode` gate at lines 326-343 correctly suppresses rich context fields for non-internal installs. These are the right patterns.

**Fix:** In `normalizeStore`, catch `normalizeFeedback` errors per item and skip (or quarantine) the bad entry rather than propagating the throw. A lenient-load / strict-create split is the standard defensive pattern:
```js
feedback: store.feedback.flatMap((item) => {
  try { return [normalizeFeedback(item, { telemetryMode })]; } catch { return []; }
})
```
Add a test: ledger with one malformed item (missing `tryingToDo`) must not block `listFeedback` for the remaining items.
