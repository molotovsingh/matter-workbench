## The headline: a new P1 (first since Run 6)

**R9-1 — `/api/file-raw` crashes the whole server on a post-header stream error (P1, availability).**
`routes/app-shell-routes.mjs:292` (DB mode) and `:303` (filesystem mode) do `raw.stream.pipe(response)` **after** `response.writeHead(200, …)`, with **no `.on("error")` on the source and no `response.on("close")`**. In filesystem mode the source is a lazily-opened `fs.ReadStream` (`workspace-service.mjs:254`) that can emit `'error'` **after** headers — file truncated/deleted mid-read, disk I/O error, or **`EMFILE` from fd exhaustion** (see R9-2). An `'error'` event with no listener throws; because it fires *asynchronously* after the awaited handler promise already resolved, the `server.mjs:356` try/catch cannot catch it, and **there is no `process.on("uncaughtException")` guard anywhere in runtime source** (verified: `rg` = 0 hits). Result: **the Node process crashes, dropping every in-flight request for every user.** Empirically reproduced on Node 26.3.0 (`uncaughtException` → exit). DB mode (`Readable.from(bytes)`, in-memory) effectively cannot emit a post-header error, so this is a **filesystem-mode** crash.
**Why P1 now (escalated from Run 7's `F17` P2 brittle*):** the full-process crash + the R9-2 fd-leak that makes `EMFILE` reachable under ordinary client-abort load = a remotely-triggerable DoS, not a rare edge. **Run 8 fixed exactly this (collapsed both sites into `sendRawFileStream` with a listener) — that fix was never ported to this line.**
**Blast-radius calibration (checked):** prod runs under systemd with `Restart=on-failure` (`deployment/private-vm/matter-workbench-runtime.service:12`; the security check even enforces it), so a single crash is *dropped in-flight requests for all users + restart latency*, not a permanent outage. What holds this at **P1** rather than "blip" is **recurrence**: R9-2 leaks an fd on every aborted large-file request, so under sustained client churn the crash *repeats* after each restart — a self-sustaining availability hazard, not a one-off.
**Fix:** replace both `raw.stream.pipe(response)` with `await pipeline(raw.stream, response)` (the repo *already* uses this correctly at `static-routes.mjs:61`) — `stream.pipeline` handles source errors and destroys both streams on premature close. Collapse the two sites into one helper while you're there.

## New findings (this delta)

**R9-1 — `/api/file-raw` post-header stream-error crash (P1).** See headline. `routes/app-shell-routes.mjs:292,303`. **Fix:** `pipeline()` per `static-routes.mjs:61`.

**R9-2 — Raw-file source stream leaks an fd on client disconnect (P2).** Same two sites: no `response.on("close")` → on a mid-stream client abort the `fs.ReadStream` is never destroyed; `source.destroyed === false` after abort (empirically confirmed). Under load this exhausts fds → `EMFILE`, which **cascades into R9-1** (the open error fires after `writeHead` → crash). DB mode leaks an in-memory buffer (GC-reclaimed), less severe. **Fix:** the same `pipeline()` change destroys the source on premature close.

**R9-3 — `captureHeartbeat` awaits Postgres-backed providers *inside* the store-mutation lock (P2, new F11-class).** `private-beta-heartbeat-service.mjs:42-53` runs its mutator inside `writeMutatedStore → withStoreMutation` and **`await`s `deploymentProvider()` and `journeyProvider()` within the lock.** `journeyProvider` = `buildHeartbeatJourneyContext` (`server.mjs:444`) reads 3 ledgers + per-matter health for up to 8 matters, **Postgres-backed in runtime-DB mode**. So the heartbeat store's serialized mutation queue is held across multi-ledger + DB I/O; a pg stall wedges the queue (the tick deadline releases the re-entrancy guard but not the lock-holder). Bounded to **P2** because the only caller is the background retry tick + tests — **no request path is affected.** **Fix:** `await` both providers *before* `writeMutatedStore` and pass the results into the mutator (verified safe — the mutator at `:55-79` only pushes a new record, never reads `store`).

**R9-4 — Redaction divergence, both directions (P2 risky*, cluster; was F14/R8-1).** The canonical `shared/secret-redaction.mjs` is the only filter on most egress paths, yet it **lacks the bare `AIza…` Google-key pattern** that the repo's own `private-beta-ui-hardening-pass.mjs:434` knows — so a bare Google key in any error/log/telemetry string reaches mothership un-redacted (`signal details.errorMessage`, `feedback context`, `mothership/report.mjs`). Conversely, `job-status-service.mjs:288-293` and `private-beta-observability-service.mjs:229-235` keep **private lists that lack the postgres-URL pattern** the shared redactor has, and surface `job.errorMessage`/`metadata` into the superuser observability view. **Reachability is genuinely uncertain in both directions** (needs the specific token shape to land in an error string), so individual rows sit at P3 — but the *cluster* is a P2-worthy, ~15-line root-cause fix and a recurring theme. **Fix:** add the `AIza…` rule to `shared/secret-redaction.mjs` **and** its React twin (the parity test keeps them aligned), then delegate the two stragglers to `redactSensitiveText`.

**R9-5 — `runtime-db-storage-service.mjs` god-module (P2 overgrown, carried F15r).** ~2,245 lines fusing five altitudes: psql transport (`queryJson`/`parsePsqlJson`), a hand-rolled ~700-line SQL-string DSL (`build*Sql`/`*UpsertSql`), workspace-tree algorithms, path/domain classification, and materialize orchestration. **Fix:** extract `runtime-db-psql.mjs` (transport) and `runtime-db-storage-sql.mjs` (the builders + escapers), leaving the factory as orchestration.

**R9-6 — Materialized write is read-modify-write with no concurrency guard (P2 brittle*, carried, watch).** `runMaterializedMatterWrite` (`runtime-db-storage-service.mjs:447-501`) materializes a baseline → mutates a temp dir → diffs → persists; each `persist*` is transactional, but the baseline snapshot is not locked. Two concurrent writes on the same matter both snapshot the same baseline → last-writer-wins. **Fix:** matter-level advisory lock / `SELECT … FOR UPDATE` held through persist, or an optimistic version guard on the upserts. (Related: **R9-6b**, N+1 — materializing an N-file matter spawns one `psql` per file serially, `:550-557` → `:1034`; correctness fine, perf watch.)

**R9-7 — F2 + migrations 017/018/003 are verified at the *string tier only* (P2 test-now, T10 — the carried "honest asterisk").** The migration test `assert.match`es the `.sql` text; the service test mocks `spawn` and asserts the generated tombstone SQL **string** (`runtime-db-storage-service.test.mjs:456-466`) — the SQL is never executed. `scripts/db-runtime-write-smoke.mjs` exists but has **zero** `superseded_at` coverage. **R9-8 — `preparationErrors.ts` is a third, divergent, untested redaction path that leaks into user text *and* server telemetry (P2 risky*, T7).** `react-ui/src/lib/preparationErrors.ts:16-21` re-implements redaction with 3 inline regexes and **does not** call the canonical `redactSensitiveText`. Empirically (transpiled + executed) it **fails to mask**: `postgres://user:pass@…` passwords, non-`sk-` `Bearer` tokens, `mwb_ing_…` ingestion tokens, and `apiKey: value` colon-form keys — all of which the canonical twin catches. ## Themes (movement + new)

- **T11 — streaming/resilience boundary (NEW, and it owns the P1).** Risk concentrated at the one place the server hands a Node stream to the socket: `/api/file-raw` pipes bare, with no error listener, no close handler, and no process-level guard behind it — while a sibling route (`static-routes.mjs:61`) already does it right. This is the classic "trust ≠ resilience" split: output handling is correct, failure handling is absent.
- **T7 — twin drift: regressed relative to Run 8.** The codex line nailed the *shared-module* twins but **did not port the consumer de-twinning**: a NEW divergent redaction path (`preparationErrors.ts`, R9-8), the redactor stragglers (R9-4), and the route-helper twin that has now *drifted* (`allowMissingActive`, R9-11). The shared modules are one home; the consumers are not all pointed at them.
- **T8 — write-path integrity: F2 closed in DB mode, structural debt carries.** Supersession is atomic and single-entry, but the god-module (R9-5), the read-modify-write race (R9-6), and the N+1 reads (R9-6b) all live in the one file that absorbed most of this delta.
- **T9 — telemetry egress: closed on drain, one new capture-path leak.** The drain pattern is clean; the NEW heartbeat capture path re-introduced slow I/O under a store lock (R9-3).
- **T10 — string-matching tests: the same honest asterisk.** F2's correctness rests on SQL that is only string-asserted, never executed against Postgres (R9-7). Unchanged from Run 8; still the top follow-through.

**Meta-observation.** This delta is a clean natural experiment: the same fix queue, re-implemented independently. The verdict — **shared-abstraction hygiene transferred; boundary/consumer hygiene did not.** Every new *contract module* is right-sized and matches the verified version; every place a *consumer* had to adopt it (streaming, redaction, route helpers) is where the regressions and the lone P1 live. Risk is at the seams, not the cores — exactly where the themes predicted.
