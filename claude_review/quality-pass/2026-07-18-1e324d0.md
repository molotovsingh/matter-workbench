## The headline: both P1s cleared with executed-Postgres evidence — and the residual risk has moved to the *third* pass

**Both Run 11 P1s are verified cleared or structurally addressed, and 13 of the 26 carried items cleared outright.** The custody-fabrication SQL (R11-1) now gates every write on the actual transition and is proven by a real-Postgres replay test that runs the mutation through a restricted, RLS-enforced role — the exact evidence tier whose absence let the bug survive last run. The upload write-queue (R11-2) is matter-keyed with a genuine cross-process advisory lock, race-tested with two independent service instances. T14 — "what happens the second time?" — was the review heuristic of Run 11, and this delta systematically paid it down: recurrence reopens signals, research answers run the Ask citation guard, retries 409 on matter mismatch, commit-retry re-enqueues, crash-looping jobs fail closed.

But the pattern didn't vanish; it **receded one level**. The new P2s live on the *third* pass — the retry of the retry, the bookkeeping of the reopen:

- The commit-retry re-enqueue (the R11-15 fix) is a **silent no-op when the prior extract job failed terminally** — the on-conflict upsert never resets a terminal row, so the one scenario a user would actually retry stays wedged (R12-2).
- The lost-intake race R11-2 closed for upload writers **survives through a different door**: the story worker still does an unlocked cross-transaction read-merge-write of `matter.json` (R12-1).
- A reopened signal carries the *resolver's* `operatorStatus` forward, so the report attributes the live incident to the operator who closed it (R12-6).

And a new structural theme emerged (**T15 — single-door invariants**): several fixes enforce their invariant only in caller discipline, not in the data layer — the commit UPDATE has no status predicate (the advisory lock is the only guard), the enqueue upsert trusts its caller about terminal rows, receipts default open on missing metadata. Each is fine until the second caller arrives.

Finally, **T10 (string-tier tests) split in two**: the server side leapt a tier (executed-Postgres integration tests, behavioral validators, sabotage-grade rejection tests), while the react-ui reconnect hardening — this cycle's most delicate second-pass logic — is pinned almost entirely by **regex-over-source tests** that execute nothing (R12-3).

### P2 — the third-pass residue

**R12-1 — The matter.json read-merge-write survives through the story-worker door, outside the new lock (P2, risky, T8×T14).**
`server.mjs:789-802` and `routes/matter-workflow-routes.mjs:1374-1389` — the dispute-story worker job and the story route read `matterJson`, run a long LLM operation, then write the whole object back via `persistMatterJson` → `persistMaterializedFiles` with **no `withSerializedMatterWrite` and no advisory lock**. An add-files commit that merges a new intake into `matter.json` during that window is overwritten with the pre-upload snapshot — the exact lost-intake failure R11-2 described, through a door the fix didn't cover. Verified in code by the storage reviewer. **Fix:** route `persistMatterJson` through `withSerializedMatterWrite`, and re-read + shallow-merge the intakes array inside the locked section instead of writing the caller's stale snapshot wholesale.

**R12-2 — A terminally-failed extract job turns the commit-retry re-enqueue into a silent no-op (P2, risky, T14 — defeats the R11-15 fix).**
`runtime-db-processing-job-store.mjs:41-45` — `enqueueProcessingJob`'s on-conflict clause updates only matter_id/priority/progress/updated_at, never status/attempt_count/run_after. Scenario: commit succeeded, extract ran and failed terminally (attempts exhausted). User retries commit; `alreadyCommitted` dutifully re-enqueues (`runtime-db-storage-service.mjs:414-416`) — the upsert lands on the failed row and changes nothing the claimer looks at; the sweep re-asserts `failed`. The preparation chain is permanently wedged **in exactly the scenario a user would invoke the retry for**. **Fix:** in the on-conflict clause, when the existing row is terminal (`failed`/`cancelled` at minimum), reset `status='queued', attempt_count=0, run_after=now(), error_*=null, finished_at=null`.

**R12-3 — The react-ui second-pass hardening is pinned by regex-over-source tests that execute nothing (P2, brittle, T10).**
`test/react-auto-preparation.test.mjs` — ~49 of ~264 lines are `assert.match(runnerSource, /…/)`: the poll-error bound (`:63`), the backend-id match (`:196-201`), the transient classifier. A transposed comparison, an off-by-one in the bound, or `backendJobId` never being populated server-side would all pass green. This is the same evidence tier that hid both Run 11 P1s — now concentrated on this cycle's most delicate client logic, right after the legacy suite's 19.8k lines of behavioral coverage were deleted. The repo already owns the antidote: `test/react-theme.test.mjs` transpiles and *executes* the module. **Fix:** transpile `autoPreparationRunner.ts`, inject a scripted `api` mock (poll errors then recovery; failed-then-queued sequences), assert emitted progress states and thrown errors. Sabotage check: flip `>=` to `>` in the poll-error bound — today no test fails.

## Themes

- **T14 — second-pass divergence: paid down a level, not extinguished.** The fix cycle targeted this theme by name and cleared its worst instances (replay, recurrence, research bypass, retry mismatch, crash-loop). What remains is strictly *deeper*: the retry **of the retry** (R12-2), the bookkeeping **of the reopen** (R12-6), the fallback **of the reconnect** (kind-latch). The heuristic sharpens for Run 13: *when a second-pass fix lands, ask what happens when the second pass itself repeats.*

- **T15 — single-door invariants (NEW).** Several invariants are enforced only in caller discipline, with the data layer accepting anything: the commit UPDATE trusts the advisory lock (no status predicate, `…persistence-sql:136-148`); the enqueue upsert trusts callers never to re-enqueue terminal work (`job-store:41-45`); receipts trust every job to carry skill metadata (`native-skill-run-receipts.mjs:28`); `SET_CONFIG` trusts every dispatcher (`AppContext.tsx:30`); the lifecycle UPDATE trusts payloads to carry no operator state (`store.mjs:174`).
